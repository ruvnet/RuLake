# ipfs-backend — A Deep Introduction

## TL;DR

`crates/ipfs-backend/` is a sibling crate that implements ruLake's `BackendAdapter` trait against IPFS, but stores only the `table.rulake.json` bundle — the small, witness-anchored sidecar — and never the vector bodies, which stay on whichever backend already serves them. It runs in three modes (kubo HTTP RPC, gateway-only, or kubo with gateway fallback), maps the resolved CID into `Generation::Opaque(String)` so the existing witness recipe is unchanged, and treats `data_ref ≠ "ipfs://{cid}"` as a hard refusal (`IPFS_BUNDLE_CID_MISMATCH`) after the focused security review surfaced R-IPFS-1 as a CID-substitution vector. The result is a content-addressed, network-public distribution plane for the cache anchor itself, sized for the bundle's 64 KiB cap and the single-block fetches that come with it.

## Introduction

ruLake's bundle is small and load-bearing in equal measure. A `table.rulake.json` carries `(data_ref, dim, rotation_seed, rerank_factor, generation, rvf_witness, pii_policy, lineage_id, memory_class)` and is bounded by `MAX_JSON_BYTES = 64 * 1024` at `crates/core/src/bundle.rs:218` — a few hundred bytes in practice, with two orders of magnitude of headroom. Because the witness is a SHAKE-256(32) digest over the four content-shaping fields plus the variant-tagged `Generation` (`crates/core/src/bundle.rs:362`-area, `crates/core/src/bundle.rs:73`-area for the variant-tag fix from the 2026-04-23 audit), two ruLake instances independently constructing the same bundle produce the same witness without ever comparing payloads. That property is what makes cross-deployment cache sharing safe in the first place — the bundle, not the bytes, is what travels.

What was missing before ADR-005 was a *transport* for the bundle that matched its content-addressed shape. The first cloud backend, `crates/gcs-backend/` (commit `c706dc6`), addressed Parquet objects by `gs://bucket/key` URIs and per-object generation tokens. That works for one cloud and one tenant, but it carries an authentication graph — IAM roles, signed URLs, bucket-level policies — that has to be settled before two parties can share a cache anchor. IPFS is the natural fit for the opposite property: you do not need to know who pinned a CID to fetch it. If the CID resolves, the bytes are exactly what they were when the witness was computed, because the CID *is* a hash of the bytes. The naming axis (where the bundle lives, who fetches it, through which gateway) becomes orthogonal to the trust axis (whether the bundle's witness verifies against its own fields).

The historical context is that several adjacent decisions had to land first. The witness had to be cryptographically sound — that landed with the `Generation` variant tag in `crates/core/src/bundle.rs:73`-area, closing a collision between `Num(7)` and `Opaque("\x07\0\0\0\0\0\0\0")` that the security audit caught. The MCP server's `rulake://bundle/{backend}/{collection}` resource contract had to commit to a cheap `current_bundle()` override (ADR-004), because IPFS body fetches over a public gateway can be hundreds of milliseconds and a DAG walk would push that into seconds. The crate-layout discipline from ADR-001 — sibling crates, no root workspace, no `*.workspace = true` — had to be in place so the IPFS dependencies (`reqwest`, `cid`, `multibase`) did not bleed into every consumer of `rulake` core. By the time ADR-005 opened, the question was no longer "is content-addressed distribution a good idea" but "what is the smallest crate that picks kubo as default, falls back to public gateways, and reuses the bundle's existing trust property without inventing a second one."

The reason this matters *now*, rather than at some abstract later, is operational. The agent-developer persona that ADR-006 surfaces wants to publish a bundle from a browser tab, paste a CID into a peer's tab, and have that peer's `verifyBundleJson` re-derive the same SHAKE-256 against the bytes the gateway delivered. There is no other distribution plane in the ruLake stack that lets that flow happen without an HTTP server, a bucket policy, or a CDN configuration. IPFS is the one — but only if the backend honors the witness/CID binding strictly, which is the load-bearing decision the focused security review forced.

## The decision in detail

The crate ships as `ruvector-rulake-ipfs` v0.1.0 at `crates/ipfs-backend/`, sibling to `crates/gcs-backend/`. Three operating modes, picked by the operator at construction time (`crates/ipfs-backend/src/backend.rs:39`-area):

- `Mode::Kubo` — talks to a kubo HTTP RPC (default `http://127.0.0.1:5001`), reads via `POST /api/v0/cat`, writes via `POST /api/v0/add` followed by `POST /api/v0/pin/add`. Optional bearer token threaded through `Mode::Kubo { api_token }` for kubo nodes behind a Caddy/nginx auth layer.
- `Mode::Gateway` — read-only, against a public IPFS Foundation gateway (`https://ipfs.io` by default; `dweb.link`, `w3s.link` documented as alternatives; Cloudflare's `cloudflare-ipfs.com` deliberately excluded because it was decommissioned 2024-08). `publish_bundle` errors at the trait boundary with `RuLakeError::Backend` so a caller in this mode cannot accidentally write through a gateway that does not accept writes anyway.
- `Mode::KuboWithGatewayFallback` — kubo first; on a kubo `cat` failure, fall back to the gateway with a `tracing::warn!` line carrying `cid` and `error` so the degradation is operator-visible (`crates/ipfs-backend/src/backend.rs:225`-area).

Two notable implementation choices defended by the ADR. First, the dependency on `ipfs-api-backend-hyper` was *removed* before v0.1 shipped — it transitively pulled `multihash 0.17` → `core2 0.4` (yanked), and the kubo HTTP RPC is small enough (`add`, `cat`, `pin/add`) that talking to it via `reqwest` directly is ~50 LOC of multipart upload and JSON parse (`crates/ipfs-backend/Cargo.toml` header comment). Second, the backend's `pull_vectors` deliberately errors (`crates/ipfs-backend/src/backend.rs:331`): IPFS is the bundle distribution plane, not the vector body plane. Operators wire IPFS for the witness round-trip and a sister backend (`gcs`, `fs`, `local`) for the bytes. ADR-155's cache-first stance says backends are interchangeable so long as their generation tokens are reliable; IPFS's role here is to carry the generation token cheaply, not to serve a 50 MB Parquet over a public gateway.

What got rejected. Embedded full-node Rust IPFS (`rust-ipfs`, alpha; `iroh`, IPFS-compat layer not shipped) — both pull a libp2p stack, DHT routing tables, NAT traversal state, and peer-id key material into the serving binary for no upside when the operator already has a kubo daemon. Vector-bodies-on-IPFS — technically possible via UnixFS, but a 100k×128 f32 collection is ~50 MB, which is `~10–60 s` on a public gateway cold-fetch and breaks the 1.02× tax envelope from `BENCHMARK.md`. The MCP server's `transfer_ipfs-resolve` tool — that resolves IPNS names to CIDs and is fine as a config-time helper, but using it in the read path means every bundle fetch goes through a public resolver with no auth and no SLA.

The load-bearing trade-off is the witness↔CID binding. The bundle's `rvf_witness` is SHAKE-256; the CID is sha2-256 multihash; they are different hash functions and cannot be made equal. The mapping the ADR commits to is: `data_ref` becomes `ipfs://<cid>`, `generation` becomes `Generation::Opaque(<cid>)`, and the witness is recomputed through `RuLakeBundle::new` so it reflects the IPFS-side fields. R-IPFS-1, the security finding from the focused review, was that an earlier `fetch_bundle` was warn-only on `data_ref ≠ ipfs://{cid}` — a CID-substitution attacker could re-pin a legitimately-witnessed bundle under a different CID and serve it back to a caller that recorded the original. The fix in commit `56b497b` is a hard refuse with code `IPFS_BUNDLE_CID_MISMATCH` (`crates/ipfs-backend/src/backend.rs:284`-`303`).

## Capabilities

**Bundle-publishing.** An operator computes a bundle locally, calls `IpfsBackend::publish_bundle(collection, &bundle)` (`crates/ipfs-backend/src/backend.rs:260`), and gets back a CIDv1. The flow is `bundle.to_json()` → `kubo_add` (multipart POST with `cid-version=1`) → `kubo_pin_add`. The CID is recorded against the collection through `record_cid` so subsequent `fetch_bundle`/`current_bundle` calls resolve it without operator re-entry. Republishing identical bytes returns the same CID by construction — content addressing means the network does the dedup.

**Cross-deployment cache priming.** Two ruLake instances on two hosts both register the same `(collection, cid)` mapping (or one publishes and shares the CID with the other). Each instance's `current_bundle` resolves the CID through its configured mode, parses the JSON, verifies that the bundle's `data_ref` matches `ipfs://<cid>` (refusing on mismatch), and constructs a re-anchored `RuLakeBundle` through `RuLakeBundle::new`. Because the witness recipe is purely a function of bytes, both instances derive the same `rvf_witness` and share the cache pointer through `crates/core/src/cache.rs::install_prebuilt_interned`. No bucket policy, no signed URL, no shared IAM — just a CID and a witness that happens to verify.

**Gateway-only sandbox / CI.** A CI job that needs to pull a published bundle for verification but cannot run a kubo daemon constructs `IpfsBackend::gateway_only(id, "https://ipfs.io")`. The mode rejects `publish_bundle` at the trait boundary, so a runaway test cannot accidentally try to write through a gateway. Reads go straight to `gateway_cat` (`crates/ipfs-backend/src/backend.rs:483`).

**Worked example.** Imagine a research collaboration where two universities both compute a vector index over a shared corpus of ~50k documents stored as Parquet on each institution's own GCS bucket. Each institution's ruLake registers a `GcsParquetBackend` for the bytes. One institution computes the bundle, pins it on its kubo daemon (`publish_bundle`), and shares the CIDv1 with the other. The peer registers an `IpfsBackend` in `Mode::KuboWithGatewayFallback`, registers the `(collection, cid)` mapping, and calls `RuLake::current_bundle(&key)`. The IPFS backend fetches the bundle (kubo first, gateway on miss), refuses if the bundle's `data_ref` does not match the CID, and returns a re-anchored bundle whose witness verifies. The peer's cache shares the witness with the publisher's — both `cache_witness_of(&key)` calls return the same hex digest — and either institution's subsequent `search_one` against that key serves out of the same RaBitQ-compressed entry. The bytes never crossed institutional boundaries; only the 300-byte sidecar did.

## Trust & correctness contract

The trust anchor is the CID↔witness binding, enforced at fetch time. The relevant section is `IpfsBackend::fetch_bundle` at `crates/ipfs-backend/src/backend.rs:271`-`306`:

1. Resolve `(collection) → CID` from operator config (`crates/ipfs-backend/src/backend.rs:154`).
2. `cat` the CID through whichever client the mode allows (`crates/ipfs-backend/src/backend.rs:215`-`239`).
3. Parse the bytes as UTF-8, then through `RuLakeBundle::from_json` (`crates/core/src/bundle.rs:215`), which enforces the 64 KiB cap and per-field length caps and rejects `format_version > 2`.
4. **Hard refuse** if `bundle.data_ref != "ipfs://{cid}"` — emit a `tracing::error!` with `got` and `expected`, return `RuLakeError::Backend` with the `IPFS_BUNDLE_CID_MISMATCH` code embedded in the detail string (`crates/ipfs-backend/src/backend.rs:292`-`303`).
5. Return the verified bundle.

Step 4 is the load-bearing one. Witness equality alone does not catch a CID-substitution attack: an attacker who controls a pinning service can re-publish a legitimately-witnessed bundle under a different CID, and a caller that had previously recorded the original CID would silently serve from the new one. The `data_ref ↔ CID` binding is the only check that catches that — if `data_ref` is `ipfs://bafkrei…ABC` but the fetched CID is `bafkrei…XYZ`, the operator is asserting two different identities for the same bytes, and the backend refuses.

The five operator-visible audit codes are the surface of this contract: `IPFS_OK` (read succeeded), `IPFS_HTTP_ERROR` (network/HTTP failure), `IPFS_BUNDLE_VERIFIED` (`from_json` accepted and witness verified), `IPFS_FETCH_FAILED` (round-trip failed end-to-end), `IPFS_BUNDLE_CID_MISMATCH` (the R-IPFS-1 refusal). The Console emits the same codes from its WASM-local IPFS path (`ui/src/components/screens.jsx:1137`, `:1168`, `:1228`, `:1775`, `:1784`) so the browser's audit ring and the server's structured logs share a vocabulary.

The fast-path optimisation in `current_bundle` (`crates/ipfs-backend/src/backend.rs:354`-`372`) is worth calling out: when the operator pre-set both `cid` and `dim` at register time, the backend synthesises the bundle locally through `RuLakeBundle::new` without any IPFS round-trip, which honours the ADR-004 resource contract's "cheap `current_bundle()`" requirement at zero network cost. The slow path falls back to `fetch_bundle` and pays one single-block `cat` — bundles are bounded by the JSON cap to a single IPFS block (default 256 KiB), so no DAG walk is involved.

## Reference implementation status

What shipped, with paths.

- **v0.1 crate** at `crates/ipfs-backend/`, package name `ruvector-rulake-ipfs`, version `0.1.0`. Three modes (`Kubo`, `Gateway`, `KuboWithGatewayFallback`); `BackendAdapter` impl with `id`, `list_collections`, errored `pull_vectors`, `generation` (stable hash over the CID), and a CID-aware `current_bundle` override. `publish_bundle`, `fetch_bundle`, `add_and_pin`, `cat` as backend-level helpers. Source: `crates/ipfs-backend/src/backend.rs:1`-`551`.
- **Hard-refuse on CID mismatch (R-IPFS-1)** landed in commit `56b497b` (`sec(shipping-substrates): fix R-IPFS-1 + R-MCP-1 from focused review`). The relevant block is `crates/ipfs-backend/src/backend.rs:284`-`303`.
- **Criterion bench harness** landed in commit `8ce3689` (`perf+sec(shipping-substrates): bench harness + focused review for gcs/ipfs/mcp-server`). The bench file is `crates/ipfs-backend/benches/verify_bundle.rs`.
- **Reqwest-direct kubo client.** The header comment in `crates/ipfs-backend/Cargo.toml` documents why `ipfs-api-backend-hyper` was rejected (transitive `multihash 0.17 → core2 0.4` yank) and why a ~50 LOC `reqwest` shim is the v0.1 client.
- **Offline test surface.** The crate ships four offline tests via `mockito` against a fake kubo + a fake gateway. Live testing is gated behind `RULAKE_IPFS_LIVE_TEST=1` + `RULAKE_IPFS_KUBO_API`, so CI does not require a kubo daemon.
- **CID shape validator.** `validate_cid_shape` (`crates/ipfs-backend/src/backend.rs:525`) catches empty / whitespace / control-byte CIDs at register time so a misconfig dies cleanly before the first network call. kubo and the gateway are the canonical validators; this is just a fast-path.

What did *not* ship in v0.1, deliberately. The deployment annex (ADR-005 §9–§11) for the single-node kubo on `ruv-dev` GCP — documented, not provisioned. The `pinning-service` Cargo feature for Pinata / Storacha / Filebase — gated off by default to keep the v0.1 surface narrow. The encryption envelope for confidential bundles — documented in ADR-005 §8 as an `examples/` exhibit because operators will ask, but not part of the backend itself. IPNS resolution in the read path — the operator resolves IPNS once at config time; the backend reads CIDs.

## Composition with the rest of ruLake

`crates/ipfs-backend/` slots into the `BackendAdapter` graph the same way `local`, `fs`, and `gcs` do. From the lake's perspective it is a source of `current_bundle` answers; the extra contract — that the IPFS layer carries the witness sidecar and *not* the vectors — is encoded by `pull_vectors` errors with a structured message pointing the operator at the body-store backend they should pair it with.

Three concrete composition points. First, the witness recipe. `IpfsBackend::current_bundle`'s fast path constructs a `RuLakeBundle` through `RuLakeBundle::new` (`crates/core/src/bundle.rs:166`), which calls `compute_witness` (`crates/core/src/bundle.rs:362`). The same SHAKE-256 digest that anchors a Parquet table or a Local fixture anchors the IPFS-resolved bundle, which is what makes cross-backend cache sharing through `crates/core/src/cache.rs::install_prebuilt_interned` correct without a witness-alias table.

Second, the federation primitive. `RuLake::search_federated` (`crates/core/src/lake.rs:521`) is a rayon parallel walk over `(backend, collection)` pairs. An `IpfsBackend` is just another `(backend, collection)` registered in the lake — the federation code does not know the layer underneath is content-addressed. What changes is the `Consistency` posture an operator should pick: ADR-155's `Consistency::Eventual { ttl_ms }` is the recommended default for IPFS-served collections because `Fresh` triggers a generation check on every search, and on IPFS the generation check is a network call (or a stable_hash over the CID, in `IpfsBackend::generation` at `crates/ipfs-backend/src/backend.rs:341`).

Third, the MCP-server path. ADR-004's `rulake://bundle/{backend}/{collection}` resource resolves through `RuLake::current_bundle` (`crates/core/src/lake.rs:179`), which delegates to `BackendAdapter::current_bundle`. For an IPFS-registered backend, the resource serves either the locally-synthesised bundle (fast path, no round-trip) or the verified-and-re-anchored bundle from `fetch_bundle` (slow path, one single-block fetch). The R-IPFS-1 refusal propagates verbatim — a tampered IPFS resource fails the MCP request with a refusal, not a corrupted bundle.

The Console (ADR-006) consumes the same surface from the browser via the WASM-local IPFS path (`ui/src/lib/storage/ipfs.ts`, mirrored from this crate), and the App Store screen at `ui/src/components/screens.jsx:2074`-`2084` lists `ipfs-backend` as `SHIPPING` with the one-liner "Publish table.rulake.json sidecars by CIDv1 over kubo. Bundle-only mode (vector bodies stay in the body-store backend). Three modes: kubo / gateway-only / kubo + gateway-fallback."

## Open questions

The deployment annex (ADR-005 §9–§11) is documented but not provisioned — the single-node kubo on `ruv-dev` GCP is a multi-page deployment script, not yet executed. Pinning-service quotas (Pinata's tiered pricing, Storacha's UCAN-based auth) are kubo's problem in v0.1; the v0.2 reopener is the Pinning Services API `pins?status=...` list-and-prune workflow. The two-bundles question — `W_pre` (the locally-computed bundle pointing at `gs://...`) and `W_post` (the IPFS-anchored bundle pointing at `ipfs://<cid>`) are different witnesses by construction, and ADR-005 §3.4 deliberately does not build a witness-alias table because that would add a trust layer (someone has to assert the alias) on top of a system designed to need none. Body-on-IPFS is the v0.3 reopener behind a dim-1024 / count-100k workload that v0.1 cannot serve usefully. Per-CID ACLs on the kubo HTTP API are not natively supported by kubo itself; the daemon-level auth in ADR-005 §11 is the v0.1 control.
