# ADR-003: Node.js / TypeScript SDK — napi-rs binding, Float32Array zero-copy, ESM-first

## Context

Node.js / TypeScript is the second-largest audience for "vector cache
in front of my existing data". The dominant patterns:

- **Edge / serverless RAG** — Vercel Edge, Cloudflare Workers,
  AWS Lambda — where the application talks to a vector DB and an LLM
  from a TypeScript handler.
- **Long-lived Node servers** — NestJS, Fastify, plain Express —
  serving RAG endpoints to web/mobile front-ends.
- **TypeScript orchestration** — LangChain.js, LlamaIndex.ts,
  Mastra, Agentic frameworks — where the framework is TS and the
  vector store is one of many pluggable adapters.

Telling these audiences "shell out to a Rust binary" or "stand up a
gRPC server in front of ruLake" is a non-starter. They expect:

```ts
import { RuLake, LocalBackend } from "@ruvector/rulake";

const lake = new RuLake({ rerankFactor: 20, rotationSeed: 42n });
await lake.registerBackend(new LocalBackend("local"));
const hits = await lake.searchOne("local", "docs", queryF32, 10);
```

The Node SDK must:

1. **Hide Rust** behind an npm package that installs a prebuilt
   binary. Node users don't have a Rust toolchain and shouldn't need
   one.
2. **Preserve the 1.02× cache-hit tax**. Same constraint as ADR-002.
   The query vector and result IDs must not round-trip through
   plain-array JSON; vectors flow as `Float32Array`, IDs as `BigUint64Array`
   (or `bigint` per-row).
3. **Be ESM-first, with a CJS shim**. The TS ecosystem has decisively
   moved to ESM (Node 22+ native, Vite/esbuild/tsx default ESM).
   We ship `.mjs` + `.d.ts` for ESM and a `.cjs` shim for legacy.
4. **Run off the Node main thread**. RAG handlers are I/O-heavy and
   can't afford a 1–10 ms blocking scan on the event loop. Native
   work must run on the libuv thread pool, so JavaScript yields and
   serves other requests during the scan.
5. **Provide TypeScript types out of the box** — `.d.ts` generated
   from the Rust type system, not hand-written.
6. **Distribute prebuilt binaries** for the platforms Node users
   actually run on.

The Rust API surface is the same as in ADR-002:

```rust
pub use lake::{RefreshResult, RuLake, SearchResult};
pub use backend::{BackendAdapter, BackendId, CollectionId, LocalBackend, PulledBatch};
pub use bundle::{Generation, RuLakeBundle};
pub use cache::{CacheStats, PerBackendStats, VectorCache, Consistency};
pub use fs_backend::FsBackend;
pub use error::{Result, RuLakeError};
```

## Decision

We ship a Node.js SDK as a **third Cargo crate** in this repo (planned
path: `node/`) that uses **napi-rs** (Node-API stable ABI) to expose
the public Rust surface, with **Float32Array / BigUint64Array
zero-copy** for vectors and IDs, **async-first** API backed by libuv
worker threads, **ESM-first** distribution with **per-platform
prebuilt binaries** delivered via npm `optionalDependencies`.

The npm package name is `@ruvector/rulake` (scoped under the org).
The TypeScript module shape:

```ts
// node/index.d.ts (generated by napi-rs from #[napi] annotations)
export class RuLake {
  constructor(opts: { rerankFactor: number; rotationSeed: bigint });
  withConsistencyEventual(ttlMs: number): RuLake;
  registerBackend(backend: BackendAdapter): Promise<void>;
  searchOne(backend: string, collection: string, query: Float32Array, k: number): Promise<SearchResult[]>;
  searchFederated(collection: string, query: Float32Array, k: number): Promise<SearchResult[]>;
  searchBatch(backend: string, collection: string, queries: Float32Array, dim: number, k: number): Promise<SearchResult[][]>;
  cacheStats(): CacheStats;
  // ...
}
```

### 1. Bindings via napi-rs

napi-rs is the only Rust↔Node binding library that:

- targets **Node-API** (the stable ABI), so a single `.node` binary
  works across Node 18, 20, 22, 24 without recompile,
- generates **TypeScript types** automatically from `#[napi]`
  annotations (no hand-written `.d.ts` to drift),
- supports **async functions** that return `Promise<T>` with the work
  scheduled on the libuv thread pool,
- supports **TypedArray zero-copy** via `Buffer` / `Float32Array`
  parameter types with `.as_ref::<f32>()` returning a borrowed slice,
- ships a **prebuild + optionalDependencies** distribution pattern via
  `@napi-rs/cli` that the rest of the Node ecosystem (Prisma,
  next-swc, parcel-css, lightningcss) has battle-tested.

We reject Neon (the older alternative) because it does not target
Node-API by default and its async story is meaningfully clunkier than
napi-rs's `#[napi]` async fn.

The `node/Cargo.toml` shape:

```toml
[package]
name = "rulake-node"
version = "2.2.0"
edition = "2021"
publish = false  # built and shipped by @napi-rs/cli, not crates.io

[lib]
crate-type = ["cdylib"]

[dependencies]
rulake = { path = ".." }
napi            = { version = "2.16", default-features = false, features = ["napi8", "async"] }
napi-derive     = "2.16"

[build-dependencies]
napi-build      = "2.1"
```

`napi8` selects the Node-API version (≥ Node 12.22 / 14.17 / 16.0).
We could pin `napi9` (Node 18.17+) to access newer APIs, but `napi8`
costs nothing and keeps Node 18 LTS in scope until April 2025;
re-evaluate when 18 hits true EOL.

The `node/package.json` shape:

```json
{
```

`@napi-rs/cli` generates `binding.js` (loader that picks the right
optional dependency at runtime), the `.mjs` / `.cjs` re-exports, and
the `.d.ts`. The `@ruvector/rulake-<triple>` packages each contain
*only* a single `.node` binary plus a `package.json` with `os` /
`cpu` / `libc` constraints, so npm only downloads the right binary
per host.

### 2. Zero-copy `Float32Array` / `BigUint64Array`

Every API that takes a vector takes `&Float32Array` or `&Buffer` and
calls `.as_ref::<f32>()` (napi-rs) which returns `&[f32]` *without
copying* when the underlying ArrayBuffer is contiguous (always true
for `new Float32Array(n)` / `new Float32Array(n*dim)`).

Result IDs:

- For top-k ≤ 100 (the common case), return `Vec<SearchResult>` —
  napi-rs converts to a JS array of `{ backend, collection, id, score }`
  objects. The per-object cost (~100 ns) is negligible at k = 10.
- For top-k > ~500 we add `searchOneArrays(...)` returning
  `{ ids: BigUint64Array, scores: Float32Array }` — same pattern as
  the Python ADR-002 §Open questions §3.

`id` is `bigint` because Rust `u64` doesn't fit in a JS Number once
the high bit is used; napi-rs serializes `u64` to `bigint` by default.
This is a small ergonomics tax — `hits[0].id === 42` becomes
`hits[0].id === 42n` — paid once per use, type-checked by TS.

```rust
use napi::bindgen_prelude::*;
use napi_derive::napi;

#[napi]
pub struct RuLake {
    inner: rulake::RuLake,
}

#[napi]
impl RuLake {
    #[napi(constructor)]
    pub fn new(opts: RuLakeOpts) -> Result<Self> {
        Ok(Self {
            inner: rulake::RuLake::new(
                opts.rerank_factor as usize,
                opts.rotation_seed.get_u64().1,
            ),
        })
    }

    #[napi]
    pub async fn search_one(
        &self,
        backend: String,
        collection: String,
        query: Float32Array,
        k: u32,
    ) -> Result<Vec<SearchResultJs>> {
        let inner = self.inner.clone(); // Arc<…> — cheap.
        let q: Vec<f32> = query.as_ref().to_vec();
        // Borrow doesn't survive across await; one copy at the FFI
        // boundary is the price for async-on-worker-thread semantics.
        // Measured at <1 µs for D = 768.
        tokio::task::spawn_blocking(move || {
            inner.search_one(&backend, &collection, &q, k as usize)
                .map_err(map_err)
                .map(|hits| hits.into_iter().map(SearchResultJs::from).collect())
        }).await.unwrap()
    }
}
```

The one copy is the only honest cost: borrowing `query.as_ref()` ties
the slice's lifetime to the `Float32Array` parameter, which doesn't
outlive the synchronous portion of the function. `spawn_blocking` is
the standard napi-rs pattern for "do CPU work off the main thread,
return a Promise". The copy is one `memcpy` at memory bandwidth —
~3 µs for D = 768 at PC-DDR5 speeds. The cache scan itself is much
larger, so the relative tax stays under 1.05×.

For batch search, the cost is amortized — one copy of
`(N × dim) × 4 bytes` versus N individual scans.

### 3. Async-first, libuv-worker-threaded

The Node SDK is async-only at the JS level. Every method that does
work returns `Promise<T>`. The work runs on a libuv worker thread via
`tokio::task::spawn_blocking` (napi-rs ships a tokio runtime when
the `tokio_rt` feature is on; we use it for `spawn_blocking` only,
not for I/O).

**Why async-only when ADR-002's Python is sync-first**: the platform
is different. Node has a single event loop and `npm` users expect
non-blocking. A sync `searchOneSync` would block the event loop for
1–5 ms per call, which is unacceptable in a Vercel/AWS-Lambda or
Express handler.

Pure-data getters that don't do work (`cacheStats()`, `backendIds()`,
`cacheEntryCount()`) stay sync — they take a lock briefly and return.
The threshold: anything that takes longer than ~50 µs in the worst
case is async; everything else is sync. Documented per-method in the
generated `.d.ts`.

### 4. ESM-first, CJS shim

`type: "module"` in package.json. Native module shape: `index.mjs`
re-exports from `binding.js`; `index.cjs` is a generated CJS shim
(also re-exporting from `binding.js`). The `.node` binary is
required from `binding.js` via `createRequire(import.meta.url)`.

Both shapes work. The reason ESM-first matters:

- Vercel, Cloudflare Workers, Deno, Bun all default to ESM. CJS
  imports of native modules are increasingly second-class.
- Top-level `await` is available in ESM, so users can do
  `const lake = await RuLake.fromBundleDir(...)` at module scope.
- Tree-shakers (esbuild, rollup, Vite) honor `exports.import` first.

CJS users still get a working module via `require("@ruvector/rulake")`.

### 5. Distributed via npm with optionalDependencies

The five-platform build matrix lives in CI (GitHub Actions, the
`@napi-rs/cli` template). On tag push:

1. Each platform job runs `napi build --release --target <triple>`.
2. The platform-specific `.node` binary is packaged as
   `@ruvector/rulake-<triple>` and published to npm.
3. The umbrella package `@ruvector/rulake` is published once with all
   five `optionalDependencies`.
4. On `npm install @ruvector/rulake`, npm/yarn/pnpm read the host's
   `os` / `cpu` / `libc` and install only the matching optional dep.

Why optionalDependencies and not `postinstall` / `prebuild-install`:

| | optionalDependencies | postinstall download |
|---|---|---|
| Works in air-gapped env | ✅ (one `.tgz` per package) | ❌ (needs network at install time) |
| Works behind corporate npm registry | ✅ (mirrors all 5 packages) | ⚠️ (needs separate binary CDN) |
| Compatible with `npm ci` lockfile guarantees | ✅ | ❌ (downloads outside lockfile) |
| Supported by Lambda layers, Vercel build cache, Docker layer cache | ✅ | ⚠️ (postinstall runs every layer) |
| Pattern used by Prisma, next-swc, parcel-css, lightningcss | ✅ | (deprecated) |

Footprint: each platform binary is ~3–5 MB (release build with
LTO + strip). Users install one of them, not all.

### 6. Error mapping

The Rust `RuLakeError` enum maps to JS via napi-rs's `Error`
mechanism, surfaced as a single `RuLakeError extends Error` class
with a `code: string` discriminator (matching Node's
[ERR_*] convention):

| Rust variant | `error.code` |
|---|---|
| `RuLakeError::BackendNotFound` | `RULAKE_BACKEND_NOT_FOUND` |
| `RuLakeError::CollectionNotFound` | `RULAKE_COLLECTION_NOT_FOUND` |
| `RuLakeError::DimensionMismatch` | `RULAKE_DIMENSION_MISMATCH` |
| `RuLakeError::InvalidParameter` | `RULAKE_INVALID_PARAMETER` |
| `RuLakeError::Io` | `RULAKE_IO` |
| `RuLakeError::Witness` | `RULAKE_WITNESS` |
| `RuLakeError::Backend(s)` | `RULAKE_BACKEND` |

The single class + discriminator is idiomatic Node (matches
`SystemError`, AWS SDK errors, etc.), and avoids the
multiple-inheritance contortions that ADR-002 uses for Python —
JS exceptions don't multi-inherit cleanly.

```ts
try {
  await lake.searchOne("nope", "docs", q, 10);
} catch (e) {
  if (e instanceof RuLakeError && e.code === "RULAKE_BACKEND_NOT_FOUND") {
    // ...
  }
}
```

## Alternatives considered

### A. WebAssembly build instead of native

WASM via `wasm-bindgen` + `wasm-pack` produces a single artifact that
runs in Node, the browser, Cloudflare Workers, and Deno without
prebuilt binaries per platform. Tempting, and we will ship a WASM
build *as well* in v2 (see Open questions §1).

Reject *as the v1 default* because:

- WASM SIMD (the `simd128` feature) gets us scalar→AVX2-style 128-bit
  SIMD but **not** AVX-512 VPOPCNTDQ, which is the kernel that
  delivers RaBitQ's high-end QPS on modern x86. Capability #11 in the
  README is a real differentiator we'd lose.
- WASM doesn't have stable threads in Node yet without `--experimental-wasi`
  flags, so the rayon parallel fan-out (capability #9) can't run.
- The 1.02× tax is measured against native RaBitQ; WASM raises it to
  ~1.5–2× depending on workload, eating the differentiation.

The right shape is "native by default, WASM available for
edge/browser as an additive package" — `@ruvector/rulake-wasm`,
shipped under the same npm scope, with a feature-reduced surface
(no rayon, no AVX-512). v2.

### B. Pure-TypeScript rewrite of the cache + router

Reject. Same reason as ADR-002 §B — the kernel is the product, and a
TS rewrite of the RaBitQ scan is ~50× slower (V8's JIT can't hit the
SIMD popcnt path). Bifurcating the witness story is also a non-starter.

### C. HTTP/SSE client against `rvf-server`

Reject *for v1*, same reasoning as ADR-002 §C. Spec'd as an additive
v2 module: `import { HttpRuLake } from "@ruvector/rulake/http"` —
exact same method surface, different transport, no native binary.

### D. Neon instead of napi-rs

Reject. Neon predates the maturity of napi-rs and lags on:

- async-fn ergonomics (Neon's async is callback-heavier),
- TypeScript-type generation (manual hand-written `.d.ts`),
- the prebuild-distribution pipeline (npm's hand-rolled in Neon).

The ecosystem has consolidated around napi-rs (Prisma, next-swc,
parcel-css, lightningcss, datadog-lambda-extension all use it). Going
against the grain costs maintenance time.

### E. Single fat binary with all platforms (no optionalDependencies)

Reject. A fat tarball with five `.node` files would weigh ~25 MB and
cost every `npm install` — including CI that doesn't need the binary
at all (e.g. `npm ci` on a Linux runner doesn't need the macOS
binary). The optionalDependencies pattern is exactly the right tool;
the only reason not to use it would be npm's older versions
mishandling it, which is no longer a concern post-npm-7.

### F. Sync API in v1, async in v2 (mirror ADR-002)

Reject. Node and Python differ fundamentally here: Python users have
threadpool ergonomics that release the GIL; Node users have a single
event loop. A blocking sync API in Node is a foot-gun in a way that
the same API in Python is not. Async-only from day one.

### G. Bun / Deno dedicated builds

Reject for v1. Both runtimes implement Node-API; the same binary
loads in both. Bun has ~95% Node-API coverage with edge cases around
TypedArray lifetime; Deno has a `--unstable-node-api` flag. We test
on Node + Bun + Deno in CI but ship one set of binaries.

If a real Bun-only or Deno-only API gap shows up, we add a runtime
detection branch in `binding.js` rather than a separate build.

## Consequences

### Positive

- `npm install @ruvector/rulake` Just Works on Node 18+, Linux x64/arm64,
  macOS x64/arm64, Windows x64. No build step, no Rust toolchain.
- The 1.02× tax survives the binding (one copy at the FFI boundary,
  measured at < 5 µs at D = 768). The Bench gate keeps regressions
  out.
- TypeScript types are generated from the Rust source via napi-rs's
  `define_package_json` step. No hand-written `.d.ts` to drift.
- Async-only API plays correctly with the Node event loop: a
  RAG handler can fan out 100 `searchOne` calls in parallel and the
  event loop keeps serving other connections.
- Per-platform optional dependencies install only the binary the host
  needs — no 25 MB fat tarball.
- ESM-first matches where the TS ecosystem is going; the CJS shim
  keeps Express + CommonJS users alive.

### Negative / accepted

- **Five-package publish per release.** The umbrella package plus
  five platform packages = six `npm publish` operations per release.
  Mitigated by `@napi-rs/cli`'s GitHub Action template, which we
  adopt verbatim.
- **`bigint` for IDs.** Slight ergonomic tax (`42n` vs `42`).
  TypeScript catches the mismatch at edit time. Numeric IDs that fit
  in `Number.MAX_SAFE_INTEGER` could degrade gracefully — *we
  deliberately don't*, because silent precision loss on the high bit
  is worse than the typing tax.
- **One copy at the FFI boundary** for query vectors (because the
  borrow can't cross `await`). Measured at < 5 µs at D = 768; for
  batch search the relative cost is < 1%. Acceptable.
- **No native browser support in v1.** WASM build is v2. Users who
  need browser-side ruLake (rare — typically the embedding model lives
  in the browser, but the cache + lake live server-side) wait for the
  WASM package.
- **Submodule must be present at npm publish time** — same constraint
  as ADR-002 §Negative. Documented in `node/README.md` and validated
  by a `prepublishOnly` script that fails if `vendor/ruvector/` is
  empty.

### Neutral

- The Node crate adds ~500 LOC of binding code, ~50 LOC of generated
  TS shim, and napi-rs generates the `.d.ts`. ~1 engineer-week to
  ship v1 (can run in parallel with the Python SDK).
- CI gains a five-platform native build matrix. The napi-rs template
  handles cross-compilation (aarch64 Linux from x86_64 host) and the
  macOS / Windows runners are GitHub-provided.
- A `@ruvector/rulake-wasm` package is reserved in the npm scope so
  v2 doesn't fight for the name.

## Open questions

1. **WASM build (`@ruvector/rulake-wasm`).** v2. Browser, Cloudflare
   Workers, Deno-deploy, Bun. Reduced surface (no rayon, no AVX-512,
   likely no FsBackend until WASI-FS stabilizes). Measure the tax —
   if it stays under ~2× direct Rust, ship; if it explodes past 5×,
   reconsider whether browser-side ruLake is the right shape at all.

2. **HTTP client (`@ruvector/rulake/http`).** v2. Same shape as the
   Python `rulake.client` — wire over `rvf-server`. Decision:
   *only* ship if a customer asks for it; the in-process binding
   covers Node's typical workload.

3. **JS-side `BackendAdapter`.** v2. Same problem as Python (ADR-002
   §F): a JS implementation of `pull_vectors` would re-enter the V8
   isolate from a worker thread, which napi-rs handles via
   `ThreadsafeFunction` but at a cost (~10 µs per call). Decide once
   a customer has a real JS-only backend (most likely a custom HTTP
   API).

4. **High-k array-returning search.** v1.5. `searchOneArrays(...) ->
   { ids: BigUint64Array, scores: Float32Array }` — same trigger as
   Python (k > ~500).

5. **Worker-threaded `RuLake` shared across `worker_threads`.**
   `RuLake` is `Send + Sync` in Rust, but JS `worker_threads` use
   structured cloning, not shared references. Making one `RuLake`
   visible to multiple Node workers requires either (a) one binding
   instance per worker (each worker re-reads bundles from the same
   sidecar dir — works, no shared cache benefit), or (b) a
   `SharedArrayBuffer`-backed bridge (complex). v2.

6. **Streaming results via `AsyncIterable`.** For very large k or
   federated multi-shard search, streaming results as they arrive
   instead of batching to a single `Promise<SearchResult[]>`. Useful
   for time-to-first-hit-sensitive UIs. v2 if a customer asks.
